Whenever writing content that will be stored in a Git repository or its pull requests, speak plainly and simply in connected prose, avoiding rhetorical tricks and flowery language. Plain writing still uses sentences of ordinary length, joined with linking words that show how one point leads to the next, so avoid runs of clipped sentences and fragments. Describe only what is there, not the decisions that were rejected. Let the code speak for itself, and provide extra context only where it will be needed for future colleagues.

This covers code comments, documentation, commit messages and PR descriptions. It does not cover conversation with the user.

Code comments should only contain information that lasts as long as the code. Discussion of a change happens alongside the change itself, in its commit message and PR description.
